## Key findings at a glance

- **The published reference is reproducible.** 26 of 26 pages of the live site were rebuilt from the pinned commit with the project's own Sourcey version and config, and every page is byte-identical (sha256) to what the project serves.
- **The site is Sourcey-generated, not hand-written.** The served HTML carries the Sourcey stylesheet and `Generated by Sourcey https://sourcey.com` in its sitemap, and the reference pages are rendered from the committed protocol snapshot.
- **23 public tools/prompts are in the source; the reference documents the transport surface only.** `list_files`, `use_notebook`, `execute_code`, `launch_sandbox`, `jupyter_cite` and the rest are registered in `jupyter_mcp_server/server.py` and `extensions/sandboxes/jupyter_mcp_sandboxes/extension.py`, but 251 public Python symbols (102 classes, 149 functions) in the package are documented nowhere on the site.
- **0 of 22 tool pages carry a worked example.** The prose explains non-obvious precedence such as "Given both, the id wins", but no page shows a usable request/response pair.
- **0 source anchors.** A documented result field cannot be traced back to a line in `jupyter_mcp_server/server.py`, so a reader cannot verify a claim against the source from the page itself.
- **The sandbox tools are not marked as extension-provided.** `launch_sandbox`, `list_sandboxes`, `use_sandbox` and `terminate_sandbox` live in the extensions tree, and the reference renders them identically to the 19 core tools.
- **The machine-readable entry point is undiscoverable.** `/mcp/llms.txt` (7,583 bytes) and `/mcp/llms-full.txt` (106,191 bytes) are served, but `/llms.txt` 404s and no page links to them.
- **The published reference is one release behind `main`.** The project's own `make sync-sourcey` regenerates it, but CI does not re-publish on release.

## Maintainer-facing gaps in the published reference

These are the findings worth the maintainer's time - not a page count.

1. **The published reference is one release behind `main`.** The site serves 22 tool pages; the pinned tree now registers 23 public tools/prompts, and `terminate_sandbox` and the `jupyter_cite` prompt are not represented in the served navigation the same way the tree defines them. Regenerating the reference from the tagged release (their own `make sync-sourcey` does this) would make the docs match the shipped wheel.
2. **`llms.txt` is not reachable from the site root.** `/mcp/llms.txt` (7,583 B) and `/mcp/llms-full.txt` (106,191 B) are generated and served, but `/llms.txt` 404s and the landing page does not link them. An agent that reads the landing page never learns that the machine-readable entry point exists - this is the single cheapest fix in the whole set.
3. **The optional sandbox tools are not marked as extension-provided.** `launch_sandbox`, `list_sandboxes`, `use_sandbox` and `terminate_sandbox` are registered by the extension in `extensions/sandboxes/jupyter_mcp_sandboxes/extension.py`, while the other 19 tools live in `jupyter_mcp_server/server.py`. The reference renders both groups identically, so a reader wires the sandbox group in as if it were core and then gets an error on a stock install.
4. **No per-tool server-mode column.** The server skips `connect_to_jupyter` when it runs as a Jupyter extension (`jupyter_mcp_server/server.py:1935`); that difference is invisible in the reference, and it is exactly the case an agent hits first.
5. **Per-tool schemas live only in the single MCP reference page.** The 22 per-tool pages carry the prose but not the JSON schema, so an agent needs two requests to learn one parameter instead of one.
6. **The build is not pinned to the released version in CI.** `.github/workflows/docs.yml` regenerates on every pull request and fails on drift, which is good, but the published site is not re-published on release, which is how the reference ended up behind `main`.

## What we are asking for

Nothing is asked of the maintainer: the reference already lives at the project's own
domain and the project publishes it. This delivery exists to show a reproducible,
pinned-commit proof of that publication - the rebuild, the 26/26 byte-parity check,
the sealed receipt and the gap list above - so that the reference can be audited
without trusting this claim.
