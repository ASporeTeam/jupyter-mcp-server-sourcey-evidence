## Maintainer-facing gaps in the published reference

These are the findings worth the maintainer's time - not a page count.

- **The published reference is one release behind `main`.** The site serves 22 tool pages; the pinned tree now registers 23 public tools/prompts, and `terminate_sandbox` and the `jupyter_cite` prompt are not represented in the served navigation the same way the tree defines them. Regenerating the reference from the tagged release (their own `make sync-sourcey` does this) would make the docs match the shipped wheel.
- **`llms.txt` is not reachable from the site root.** `/mcp/llms.txt` (7,583 B) and `/mcp/llms-full.txt` (106,191 B) are generated and served, but `/llms.txt` 404s and the landing page does not link them. An agent that reads the landing page never learns that the machine-readable entry point exists - this is the single cheapest fix in the whole set.
- **The optional sandbox tools are not marked as extension-provided.** `launch_sandbox`, `list_sandboxes`, `use_sandbox` and `terminate_sandbox` are registered by the extension in `extensions/sandboxes/jupyter_mcp_sandboxes/extension.py`, while the other 19 tools live in `jupyter_mcp_server/server.py`. The reference renders both groups identically, so a reader wires the sandbox group in as if it were core and then gets an error on a stock install.
- **No per-tool server-mode column.** The server skips `connect_to_jupyter` when it runs as a Jupyter extension (`jupyter_mcp_server/server.py:1935`); that difference is invisible in the reference, and it is exactly the case an agent hits first.
- **Per-tool schemas live only in the single MCP reference page.** The 22 per-tool pages carry the prose but not the JSON schema, so an agent needs two requests to learn one parameter instead of one.
- **The reference is served from a path that is easy to miss.** The documentation lives under `/mcp/` of the project's main site, and `/llms.txt` (the usual agent entry point) does not exist at the site root either; an agent that looks for `llms.txt` at the domain root finds nothing. Adding a root-level `llms.txt` redirect would cost one line.
- **The per-tool pages do not state which transport they need.** `connect_to_jupyter` and the sandbox tools need a reachable Jupyter server or sandbox backend, and the reference never says so next to the tool; a reader only finds out from the tool's own error message.
- **The build is not pinned to the released version in CI.** `.github/workflows/docs.yml` regenerates on every pull request and fails on drift, which is good, but the published site is not re-published on release, which is how the reference ended up behind `main`.

## What we are asking for

Nothing is asked of the maintainer: the reference already lives at the project's own
domain and the project publishes it. This delivery exists to show a reproducible,
pinned-commit proof of that publication - the rebuild, the 26/26 byte-parity check,
the sealed receipt and the gap list above - so that the reference can be audited
without trusting this claim.
